Burst Without 503s

Request parking and an autoscaled WorkerPool on Agent Substrate. Six agents, two warm workers, and the two mechanisms that keep requests from failing when demand outruns the pool.

GKE StandardSubstrate ea273bda+router: agentgatewayatespace: ate-lab-burst

When more agents want to run than you have warm workers, Substrate has two answers on two time scales. The router parks a request for a few seconds while a worker frees up. An HPA grows the WorkerPool when the pool stays full.

The lab runs each one alone, shows where each one fails, then runs both together. Try it in the model below first, then run it for real with the runbook.

What the router returns
200Served. Slow ones waited in the lot first. 504Parked, but the budget ran out before a worker freed up. 429Pool full and parking is off: rejected immediately. 503Lot full, actor mid-transition, or a stale cached worker.

    5
    Scenario 1Parking absorbs short contention
    
        
    Check the router's parking settings. router-parking.sh sets how long agentgateway holds a request waiting for a free worker, or turns that off. It writes the router ConfigMap and restarts the router.
    
        
    bash
    
        
    Watch one request park. Port-forward the router, fill both workers, then request a third actor. It hangs. Suspend a1 from another terminal within 5 seconds and the hanging request returns 200. Wait longer and it returns 504.
    
        
    bash
    
        
    Churn load. Each actor runs request then suspend, so workers keep coming back. Expect zero failures; the 200s over 1s line counts requests that parked and then got served.
    
        
    bash
    
        
        
    Parking off. Mostly 429s now: agentgateway turns "no free worker" into 429 rate limited instead of waiting. A few 503s come from actors caught mid-suspend.
    
        
    bash
    
        
        
    Each router-parking.sh change restarts the router. That kills manual port-forwards and drops requests parked at that moment, because agentgateway drains for about 5s here. Change settings between runs. burst.sh opens its own forward each run.
    
        
    agentgateway caches an actor's worker for 5s. In churn mode the next request often lands on the old worker, which answers 421 stale; agentgateway drops the entry and resolves again. A rare 503 in churn is that retry running out.

    7
    Scenario 3The HPA adds capacity
    
        
    bash
    
        
    The HPA reads busy workers: partial plus at_capacity. A worker running its one actor reports partial, because its state compares actors with its 1000 slots. Busy workers can never exceed the replica count, and the HPA can't see actors still waiting for a worker, so each step grows the pool by at most 1 / averageValue. It also ignores a ratio within 10% of target. Try the numbers:

    8
    Scenario 4Size the park budget to cover scale-up
    
        
    Scenario 3's 504s came from the climb: a parked request gives up after 5s, but each HPA step takes longer. A 90s budget lets parked requests wait for the new workers. agentgateway uses the budget as the whole deadline for its ResumeActor retries, and it has no default request timeout, so nothing else cuts the wait short.

    Read it in Prometheus
    
        
    Run these at localhost:9091/graph across the time of Scenarios 1 to 4.
    
        
    promql
    
        
    Pool occupancy by worker state. The HPA's input is partial plus at_capacity. max drops the duplicate from the second ate-api-server replica; sum adds up sandbox classes.
    
        
    promql
    
        
    Requests resolving through ate-api right now. Each router pod has its own lot, so sum totals them. Short spikes are normal; a gauge that stays up all run means requests are waiting for workers that never free up.
    
        
    promql
    
        
    ok means a worker was found. resume_error means agentgateway gave up: here almost always a 504, or 429 with parking off. The reason isn't labelled, so match it against burst.sh's counts or the router log.
    
        
    promql
    
        
    p95 time to a worker for served requests, including time parked. It tops out at 80s: when the quantile lands in the +Inf bucket, histogram_quantile returns the highest finite bound, 80. With a 90s budget, read 80 as "80s or more" and count the longer waits directly:
